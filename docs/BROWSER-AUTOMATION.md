# 브라우저 자동화 작업 방식 (이식 가능)

> ZTO가 Play 콘솔을 자동화하며 **실패로 배운** 규칙 모음. 특정 앱·스택에 묶이지 않으므로
> 로그인이 필요한 웹 콘솔(Play·ASC·광고 플랫폼·CMS 등)을 다루는 어느 프로젝트에나 그대로 적용된다.
> 출처: ZTO ROADMAP #4, 2026-07-29~30 실측. 각 규칙 뒤 괄호는 그걸 알게 된 실패다.

---

## 0. 대전제 — 자동화는 "전부 아니면 전무"가 아니다

목표는 **무인 실행**이 아니라 **사용자가 판단할 것만 판단하게 하는 것**이다.
불확실한 한 걸음(로그인·계정 선택·2FA)에서 실패로 끝내지 말고 **사람에게 넘겼다가 이어받는다**.

---

## 1. 경로를 조립하지 마라 — 화면이 알려주는 값을 써라

가장 많이, 가장 오래 발목을 잡은 규칙이다.

- ❌ `` `${base}/app-content` `` 처럼 URL을 유추해 조립
- ✅ 페이지의 `<a href>`를 긁어 **실제 경로**를 얻고, 그 값으로만 이동

**왜**: 콘솔은 부분 경로에 관대하지 않다. `app-content`는 존재하지 않고 실제 경로는
`app-content/overview`였다. 개발자 id도 URL엔 없고 링크에만 있었다.
(→ 경로 추측으로 4회 연속 실패)

## 2. 이동한 뒤 반드시 도착지를 검증하라

없는 경로가 **404가 아니라 홈으로 조용히 리다이렉트**된다. 검증하지 않으면
"성공했다고 믿으며 엉뚱한 페이지를 읽는" 최악의 실패가 된다.

```ts
await go(formUrl)
const here = await waitForUrl((u) => u.includes('data-privacy-security'), 15_000)
if (!here.includes('data-privacy-security')) return fail('form-not-reached')
```

## 3. 고정 대기(`sleep 3s`) 금지 — 조건을 관찰하라

리다이렉트 + SPA 라우팅이 겹치면 "몇 초면 된다"가 성립하지 않는다.
빠르면 실패하고 느리면 느려지는, 양쪽으로 나쁜 선택이다.

```ts
const waitForUrl = async (test, timeoutMs) => { /* 300ms 간격 폴링, 타임아웃 시 마지막 값 반환 */ }
```
타임아웃에도 **마지막 값을 반환**해 진단에 쓴다. (→ 2.6초에 읽고 "URL이 안 바뀐다"고 오판)

## 4. 숨은 뷰는 렌더링되지 않는다

Chromium은 **보이지 않는 WebContents의 렌더링·타이머를 스로틀**한다.
무거운 SPA는 부트스트랩조차 끝내지 못한다(앵커 0개, 본문 49자).

- `webContents.setBackgroundThrottling(false)`
- **자동화 중에는 뷰를 실제로 창에 붙여 띄운다** (사용자에게 진행을 보여주는 효과도 덤)

(→ "경로 문제"로 착각해 네 번 고친 것이 전부 이 한 원인이었다)

### 4-1. 두 처방을 갈라본 기록 (2026-07-30)

위 두 줄은 **한꺼번에** 넣고 통과했기 때문에 어느 쪽이 효과였는지 모르는 상태였다.
"스로틀만 끄면 되지 않나, 띄우는 건 사용자 화면을 뺏는데"라는 의심으로 **①만 남기고 ②를 뺐다.**

**결과: 실패했다.** Play 콘솔이 `no-developer-id (a=0, text=49)` — §8이 "페이지가 아예
실행되지 않았다"로 분류해둔 바로 그 신호로 죽었다.

- `setBackgroundThrottling(false)`는 **창에 붙어 있는 뷰가 가려졌을 때**의 타이머 스로틀만 막는다
- **아예 붙지 않은 뷰**(`addChildView` 안 함)는 컴포지터가 없어 렌더 파이프라인 자체가 안 돈다
  → 무거운 SPA는 부트스트랩을 끝내지 못한다. 스로틀 설정과 무관하다

그래서 ②는 **살아 있는 규칙**이다. 자동화 중에는 띄운다.

> 남는 교훈은 그대로다: **두 처방을 같이 넣어 고쳤으면 그건 원인을 안 것이 아니다.**
> 이번엔 갈라봤고, 갈라보니 ②가 값을 하고 있었다. 30분이면 확인되는 걸 몇 달 모르고 쓸 뻔했다.
> (숨겨서 돌리고 싶다면 남은 후보는 `show:false`인 **별도 BrowserWindow** — 창은 있으니
> 컴포지터도 있다. 미검증이므로 규칙으로 적지 않는다.)

## 5. 접힌 메뉴는 DOM에 없다 — 펼치고 읽어라

Angular/React 콘솔은 접힌 영역을 **렌더하지 않는다**. 링크 수확 전에 펼친다.

```js
document.querySelectorAll('[aria-expanded="false"]').forEach(el => el.click())
```
한 번 펼치면 그 안에서 또 접힌 게 드러나므로 **여러 번**(렌더 대기 포함) 돌린다.

⚠️ 페이지 이탈을 막으려 `<a href>` 안의 토글을 제외했더니 **핵심 섹션을 통째로 놓쳤다**.
안전장치가 발견을 막을 수 있다 — 제외 조건은 최소로.

## 6. 레이아웃이 아니라 **내용**에서 출발하라

행을 찾을 때 "링크에서 조상으로 N단계" 같은 구조 가정은 페이지마다 깨진다.

- ❌ `a.closest('tr')` → 콘솔이 테이블이 아니라 div 더미면 `null`
- ✅ **찾으려는 텍스트(패키지명·식별자)를 가진 요소를 먼저 찾고**, 거기서 위로 올라가며
  목표 링크를 품은 첫 조상을 잡는다 → "가장 가까운 공통 조상"이라 구조와 무관하고 오탐이 없다

## 7. 클릭은 **라벨**로 — 클래스·구조로 하지 마라

클래스명·DOM 구조는 개편마다 바뀌지만 사람이 읽는 라벨은 오래간다.

```js
els.find(e => e.textContent.trim().toLowerCase() === 'export to csv')?.click()
```
⚠️ **정확히 일치(`===`)로 하면 안 된다.** 머티리얼 아이콘을 폰트 리거처로 쓰는 콘솔은
`textContent`에 아이콘 이름이 섞인다(`arrow_rightdashboardDashboard`, `finance_modeGrow users`).
**포함 매칭**으로 찾고 후보 중 **가장 작은 요소**를 누른다. (`=== 'export to csv'`로 뒀다가 실패)

같은 이유로 **네이티브 태그보다 ARIA role을 우선**한다. 커스텀 컴포넌트는
`<input type="radio">`가 아니라 `<div role="radio">`인 경우가 흔하고, role은 접근성 때문에 유지된다.

## 8. 진단 정보를 한 단계 더 실어라

이 목록에서 **시간을 가장 많이 아껴준 규칙**이다. 실패 메시지에 "못 찾음"만 담으면
매번 같은 층에서 헛다리를 짚는다. 한 단계 아래 사실을 함께 실으면 층이 바뀐다.

| 실패 메시지 | 알려준 것 |
|---|---|
| `app-not-found` | (아무것도 — 매칭 로직만 계속 고침) |
| `app-not-found (links=0)` | 매칭 이전에 **엉뚱한 페이지**에 있다 |
| `no-developer-id (a=0, text=49)` | 페이지가 **아예 실행되지 않았다** ← 원인 층이 바뀜 |

## 9. 공식 기계 경로가 있으면 DOM을 긁지 마라

Play 데이터 안전에는 **Export/Import CSV**가 있었다. 217문항이 기계 판독 ID와 함께 나온다.

- 읽기: CSV 내보내기 → 파싱 (선택자 의존 0, 콘솔 개정에 면역)
- 쓰기: CSV 생성 → 파일 입력에 주입(CDP `DOM.setFileInputFiles`) → 5단계 위저드를 클릭으로 따라갈 필요 없음

**DOM 스크래핑은 공식 경로가 없는 폼에만** 쓴다. 손으로 인코딩한 근사 설문(14문항)은
정본(217문항)이 생기는 순간 폐기 대상이다.

## 10. 실패는 막다른 길이 아니라 **핸드오프**

자동화가 못 하는 한 걸음은 사람에게 넘기고, 조건이 충족되면 **알아서 이어받는다**.

```ts
const handOff = async (ask, done, timeoutMs = 180_000) => {
  showBanner(ask)                       // 클릭이 통과하는 요청 배너
  while (!timedOut) {
    if (await done()) { showVeil(); return true }   // 조건 충족 → 차단 모드로 복귀 후 계속
    await wait(900)
  }
  return false
}
```

적용 자리: **로그인**, **계정 선택**(후보가 2개 이상이면 고르는 건 사람 몫), 2FA, 결제 확인.
후보가 **하나뿐이면 자동 클릭**, 여럿이면 넘긴다 — "아무거나 누르기"는 절대 금지.

⚠️ **핸드오프 조건은 "왜 못 했나"가 아니라 "못 했다"여야 한다.**
`count > 1`(여럿이라 못 고름)만 넘기게 했더니 `count === 0`(선택자에 안 잡혀 못 찾음)일 때
자동 클릭도 핸드오프도 없이 **차단막만 쓴 채 멈췄다**. 실패 사유를 열거하면 반드시 빠뜨린다.

그리고 **실패로 끝나면 브라우저를 닫아라.** 에러 메시지는 보통 앱 화면(브라우저 뒤)에 뜨는데,
"사람이 이어받게" 열어두면 정작 원인을 못 본다. 이어서 직접 할 수 있는 버튼만 남기면 된다.

## 11. 자동화 UI/UX — 막·안내·스포트라이트 (Dan 2026-07-30)

자동화가 화면을 조작하는 동안 사용자는 **무슨 일이 벌어지는지 모르고, 끼어들면 흐름이 깨진다.**
그래서 네 가지가 한 세트다.

### 11-0. 띄우되, **사용자 것을 밟지는 않는다** (2026-07-30)

자동화 중 뷰를 띄우는 건 §4-1대로 **선택이 아니라 필요**다(안 띄우면 SPA가 안 돈다).
그렇다고 사용자가 보던 것을 밟아도 된다는 뜻은 아니다 — 갈라서 지킬 수 있다:

- 자동화는 **자기 탭**에서 돈다. 사용자가 보던 탭을 그 자리에서 딴 데로 끌고 가지 않는다
- 끝나면 자동화 탭을 닫고 **원래 보던 탭으로 돌려놓는다**
- 자동화를 위해 연 오버레이/창은 자동화가 닫는다. 성공이든 실패든(§11-5)

> 처음엔 "아예 안 보이게"를 시도했다가 §4-1에서 되돌렸다. 비용은 남아 있다 —
> 1분짜리 자동화는 그동안 화면을 차지한다. 줄이려면 **자동화를 짧게** 만들거나
> (불필요한 순회 제거), `show:false` 별도 창을 검증하는 쪽이지, 붙이지 않은 뷰는 답이 아니다.

### 11-1. 진행 중임을 알리고, 아래를 클릭 못 하게 막는다
전면 오버레이로 **덮어서 차단**한다. 임베드 뷰(`WebContentsView` 등)는 OS 레이어라 앱의 React UI로
덮을 수 없고, `setIgnoreInputEvents`는 `BrowserWindow` 전용이라 뷰엔 못 쓴다
→ **페이지 안에 전체화면 fixed 요소를 주입**하면 차단이 해결된다.
내비게이션마다 날아가므로 이동할 때마다 다시 주입하고, **끝나면 반드시 걷는다**(성공·실패 모두).

### 11-2. 사람이 직접 해야 하는 단계를 같은 자리에서 알린다
로그인·계정 선택·2FA·결제 확인처럼 **자동화가 대신하면 안 되거나 못 하는** 단계가 있다.
(예: jibowner는 로그인을 사람이 직접 해야 한다.)
이때 실패로 끝내지 말고 **"여기서 직접 해주세요"**로 전환한 뒤, 조건이 충족되면 이어받는다(→ §10).

### 11-3. 안내 문구는 **브라우저 밖**에 둔다 ⚠️
페이지 안에 문구를 띄우면 **정작 눌러야 할 곳을 가릴 수 있다.**
→ 안내는 앱 자신의 UI(브라우저 뷰 바깥의 콘솔/바)에 그린다. 페이지에 주입하는 건
**시각 효과(차단막·dim)뿐**이고, **글자는 담지 않는다.**

톤을 둘로 나누면 상태가 한눈에 읽힌다:
- `run` — ZTO 진행 중(보라, 아래 클릭 차단)
- `ask` — 사람이 직접 해야 함(앰버, 클릭 열어둠)

### 11-4. 스포트라이트(대상만 부각 + 주변 dim)는 **시도했다가 폐기했다**

아이디어는 좋다 — "어디를 눌러야 하지"가 사라진다. 구현도 어렵지 않다(대상 사각형 크기의 빈 요소에
`box-shadow: 0 0 0 9999px rgba(0,0,0,.6)`으로 구멍을 판다).

**문제는 "대상을 무엇으로 특정하느냐"다.** 안정적인 방법이 없었다:
- 안내 문구와 같은 텍스트로 찾으면 → **설명 문구·제목**이 잡힌다(눌러야 할 건 그 아래 항목인데)
- 조상으로 올라가 카드를 잡으면 → 페이지마다 층이 달라 여전히 빗나간다
- 클릭 후보를 찾아 그 rect를 쓰면 → **후보를 못 찾는 상황이 곧 핸드오프의 이유**라, 정작 필요할 때 못 쓴다
- 선택자로 직접 지정하면 → 정확하지만 개편마다 깨진다(§7이 금지하는 것)

**틀린 하이라이트는 안내가 아니라 방해다.** 엉뚱한 곳이 밝아지면 사용자는 오히려 헷갈린다.
그래서 핸드오프 중에는 **페이지를 아예 건드리지 않고**(차단막도 제거) 하단 안내 바 문구에만 의존한다.
사용자는 자기가 늘 쓰던 화면을 그대로 쓰면 된다.

> 다시 시도한다면: 대상이 **명확히 하나로 특정되는 경우에만** 켜고(예: 후보가 정확히 1개인데
> 정책상 사람이 눌러야 하는 경우), 아니면 끄는 게 맞다. "밝힐 수 있으면 밝힌다"는 안 된다.

### 11-5. 실패는 **눈에 띄어야 한다**

실패 메시지를 트리 안 작은 회색 글씨로 뒀더니 사용자가 못 봤다("실패한 것 같은데 아무것도 안 뜬다").
- 실패로 끝나면 **브라우저를 닫는다** — 에러는 보통 앱 화면(브라우저 뒤)에 뜬다
- 진행 중 문구와 **다른 톤**(앰버 카드)으로 그리고, **[다시 시도]·[직접 열기]**를 함께 둔다

## 12. 세션 공유를 의심하라

앱 렌더러와 임베드 브라우저가 **같은 세션(쿠키)을 공유**하면, 렌더러가 CDN에 보내는
`<img>` 요청에도 로그인 쿠키가 실린다. 서버가 인증된 요청을 다르게 처리해 **일부만 실패**한다.

증상: URL은 `curl`로 200인데 앱에서 6개 중 1~2개만 뜸, 새로고침마다 성공 개수가 달라짐.
해결: **main(쿠키 없는 컨텍스트)에서 받아 로컬에 저장**하고 앱은 로컬에서 읽는다.
쿠키·스로틀·URL 만료·오프라인이 한꺼번에 해결된다.

> 부록: 로컬 파일을 렌더러에 낼 땐 `file://`이 아니라 **커스텀 스킴**을 쓴다.
> CSP를 열어도 렌더러 오리진이 `http`면 Chromium이 `file://`을 스킴 규칙으로 막는다.

## 13. 다운로드는 **예약 후 클릭**

클릭하고 나서 리스너를 붙이면 놓친다. 그리고 평소엔 사용자의 다운로드 폴더를 건드리지 말고,
**자동화가 스스로 받아야 할 때만** 가로채 정해진 경로에 저장한다.

```ts
const downloaded = expectDownload('data-safety.csv')   // 먼저 예약
await clickByText('Export to CSV')                      // 그다음 클릭
const file = await downloaded
```

## 14. 부재를 조용하게 만들 땐 개발자용 신호를 남겨라

이미지 로드 실패를 "조용한 빈 타일"로 바꿨더니, 사용자에겐 깔끔해졌지만 **진단이 어려워져
"자산이 사라졌다"로 보였다**. 사용자에게 조용한 것과 개발자에게 조용한 것은 달라야 한다
— UI는 조용히, 로그·상태값은 시끄럽게.

그리고 **거울상도 성립한다: 성공도 너무 조용하면 안 된다.** 217문항을 가져와 파일에 저장했는데
화면엔 스치는 회색 글씨 한 줄뿐이라, 성공했는데도 사용자는 실패와 구분하지 못했다
("뭘 어떻게 완주했다는 거야?"). **판단은 로그가 아니라 화면에서 되어야 한다** —
가져온 결과는 지속적으로 표시하고(요약 + 시각), 내용도 열어볼 수 있어야 한다.

## 체크리스트 (새 자동화를 붙일 때)

- [ ] 공식 기계 경로(Export/Import·API)가 있는가? 있으면 DOM 스크래핑 금지
- [ ] 뷰가 창에 붙어 화면에 보이는가? `setBackgroundThrottling(false)` 했는가? (둘 다 필요 — §4-1)
- [ ] 자동화가 **자기 탭**에서 돌고, 끝나면 원래 탭으로 돌려놓는가?
- [ ] 이동마다 도착지를 검증하는가?
- [ ] 고정 대기 대신 조건 관찰인가?
- [ ] 링크·경로를 조립하지 않고 화면에서 읽는가?
- [ ] 클릭 대상을 라벨/role로 찾는가?
- [ ] 로그인·선택 단계에 핸드오프가 있는가? (실패로 끝내지 않는가)
- [ ] 실패 메시지에 **한 단계 아래 사실**이 실려 있는가?
- [ ] 진행 중 차단막을 주입하고, 끝나면 걷는가?
- [ ] **안내 문구가 브라우저 밖에 있는가?** (페이지에 띄우면 조작할 자리를 가린다)
- [ ] 사람에게 넘길 때 페이지를 **건드리지 않는가?** (스포트라이트는 대상 특정이 확실할 때만)
- [ ] 실패가 **눈에 띄는가?** (브라우저 닫기 + 다른 톤 + 다시 시도 버튼)
- [ ] 비가역 액션(제출·결제·발행) 앞에 사람 컨펌이 있는가?
